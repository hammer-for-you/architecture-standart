### <a name="_qmphm5d6rvi3"></a>**Решение**
[Диаграмма контекста](standart-c4-context.puml) 

[Диаграмма контейнеров](standart-c4-containers.puml)

В ходе принятия решений и выбора технологий я руководствовался следующими принципами:
1. Мы разрабатываем MVP. Следовательно, нам нужно максимально простое решение. Поэтому мы не будем устраивать революций и затевать глобальный рефакторинг. Мы просто пристроим сбоку сервис - первый шаг на пути к разбиению монолита (-ов).
2. Мы должны по максимуму использовать уже имеющийся технологический стек, чтобы в полной мере воспользоваться компетенциями разработчиков. Новые технологии используются только тогда, когда без них не обойтись.
3. Для разработки нового сервиса предполагается использовать Java, т.к. она прекрасно подходит для разработки микросервисов, и в команде есть компетенции для разработки на Java. 
4. Для улучшения пользовательского опыта бизнес хочет улучшить быстродействие тех частей системы, с которыми взаимодейтсвуют клиенты. Для этого мы задействуем иследующие техники:
   * Масштабирование. С ростом пользовательской базы будет расти нагрузка на систему. Поэтому мы должны иметь возможность масштабироваться. К сожалению, масштабировать АБС в её текущем виде невозможно. Монолиты системы кол-центра и бэкенда интернет-банка тоже не имеет смысла масштабировать. Поэтому мы должны заложить возможность масштабирования для новых разрабатываемых сервисов.
   * Кэширование. В описании задачи указано, что ряд данных (например, справочники) грузятся очень медленно и тормозят пользовательские операции. Поэтому предлагаю закэшировать эти справочники.
5. Необходимо снизить нагрузку на АБС. В текущем состоянии АБС не выдержит создания заявок на открытие депозитов напрямую. Поэтому с целью разгрузить АБС принято решение использовать промежуточную БД для хранения заявок на открытие депозита и синхронизировать с БД АБС асинхронно - через RabbitMQ. Так же это позволит передавать в АБС не всю информацию о заявке, а только то, что нужно АБС для открытия депозита.
6. RabbitMQ выбран потому, что Kafka несовместима с бэкендом интернет-банка
7. У нас увеличивается номенклатура сервисов, потому нам нужен универсальный механизм развёртывания, мониторинга и масштабирования. Следовательно, новый функционал предлагается разворачивать в Kubernetes. Далее по мере разбиения монолитов на микросервисы туда же будут переноситься выделенные сервисы.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
1. Создание заявок на открытие депозита в АБС напрямую через API. Отклонено, т.к. есть риск перегрузки БД Oracle.
2. Kafka вмеcто RabbitMQ. Отклонено, т.к. бэкенд интернет-банка несовместим с Kafka, следовательно требуется переработка интернет-банка.
3. NoSQL в качестве БД для сервиса депозитов. Отклонено, т.к. в команде нет экспертизы для работы с NoSQL, следовательно увеличатся сроки разработки и снизится надёжность итогового решения.
4. Использование Go для разработки микросервисов с последующей миграцией кодовой базы на Go. Отклонено, т.к. в команде нет экспертизы для работы с Go.

**Недостатки, ограничения, риски**
1. Увеличивается техническая сложность решения - инфраструктуру (Kubernetes, Redis, новую БД) требуется развернуть и поддерживать. Это увеличивает затраты на разработку и потенциально может увеличить сроки.
2. Несмотря на предложенное решение по интеграции сервиса депозитов и АБС через брокер сообщений, всё равно присутствует риск перегрузки БД АБС.
3. Интеграция бэкенда интернет-банка с новым сервисом депозитов может потребовать доработок в ядре интернет-банка. В текущих условиях эти доработки может выполнить только внешний подрядчик. Это увеличивает стоимость разработки и создаёт риски срыва сроков.
